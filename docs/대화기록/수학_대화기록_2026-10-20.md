## 3. "그림"과 "SVG 템플릿"의 의미

네, 제시문(문제 본문)에 들어가는 그림을 뜻합니다. 예를 들어 "그림과 같은 부채꼴 OAB에서…"의 부채꼴 그림, 좌표평면, 도형 그림입니다.

AI는 이미지 파일을 직접 만들지 못하고 글(코드)만 출력합니다. 그림을 넣는 방법은 세 가지입니다.

| 방식 | 설명 | 장단점 |
|---|---|---|
| A. 그림 없음 | "반지름 6cm, 중심각 60°인 부채꼴"처럼 글과 수식만 사용 | 가장 안전하지만 도형 문항이 어색해집니다. |
| B. 템플릿 SVG | 미리 만든 그림 틀(부채꼴, 삼각형, 좌표평면, 입체도형 등)에 AI가 수치만 채웁니다. 코드가 SVG를 그립니다. | 그림이 정확하고, 수치와 그림이 어긋나지 않습니다. 지원하는 도형 종류가 제한됩니다. |
| C. AI가 SVG를 자유롭게 작성 | AI가 도형을 처음부터 코드로 그립니다. | 어떤 도형이든 가능하지만 길이·각도가 틀리기 쉽고, 검증이 어렵습니다. |

**제안:** 1차는 A와 B를 함께 씁니다. 중1 도형 영역(기본 도형, 작도, 평면·입체도형)은 B로 그림을 그리고, 그 밖의 영역은 글과 수식만 씁니다. C는 정확도를 확인한 뒤 고도화로 미룹니다. 교사가 직접 그림을 올리는 기능도 고도화 항목으로 둡니다.

## 4. 웹 화면의 수식과 PDF 내보내기

웹 화면에서는 수식 표시를 위해 LaTeX를 쓰는 것이 맞습니다. 다만 교사가 LaTeX를 직접 입력할 필요는 없습니다. AI가 LaTeX로 생성하고, 화면에는 KaTeX가 일반 수식 모양으로 렌더링합니다. 교사는 수식 편집 버튼으로 수정하면 됩니다.

내보내기는 PDF를 기본으로 하는 안이 현실적입니다. 근거는 두 가지입니다.
- PDF는 수식과 그림이 화면 그대로 나옵니다.
- 한글(HWP)이나 워드로 보낼 때는 수식 변환이 자주 깨집니다.

단, PDF에는 약점이 있습니다. 교사가 다시 편집하기 어렵습니다. 학교 현장에서는 한글 파일로 문항을 만드는 경우가 많아서, 한글에 붙여넣을 수 있게 해야 할 수도 있습니다.

**제안:**
- 1차: PDF로 내보내고, 화면에서 수식 복사 기능(LaTeX 또는 이미지)을 제공합니다.
- 2차(고도화): 워드(docx) 수식 내보내기를 추가합니다.
- 한글(HWP)은 지원 여부를 판단하기 위해 현장 사용 방식을 확인합니다.

**질문:** 선생님들이 만든 문항을 주로 어디서 편집·배포하시나요? (한글, 워드, 시험지 PDF 등) 이 답에 따라 2차 내보내기 형식이 달라집니다.

## 5. "어떤 수치"인지

문항 안에 들어가는 숫자 값을 뜻합니다. 예를 들어 "반지름이 6cm이고 중심각이 120°인 부채꼴의 넓이"에서 6과 120입니다.

AI가 이 숫자를 정하면 계산이 지저분해질 수 있습니다. 넓이가 36π/3처럼 깔끔하지 않게 나오거나, 중간 계산이 틀리거나, 그림과 숫자가 어긋납니다.

그래서 숫자를 정하는 방식을 둘 중에서 고릅니다.
- **AI가 직접 정함:** 빠르지만 계산이 틀리거나 지저분할 수 있습니다.
- **코드가 후보를 만들고 AI는 문장만 씀:** 코드가 "답이 깔끔하게 떨어지는" 숫자 조합을 먼저 만듭니다. 예를 들면 반지름 6, 중심각 120°입니다. AI는 이 숫자로 상황과 문장을 만들고, 정답과 풀이는 코드가 검산합니다.

**제안:** 중1은 계산 중심 문항이 많으므로 코드 후보 방식을 씁니다. 개념 설명형이나 규칙 찾기처럼 숫자가 중요하지 않은 문항은 AI가 직접 정합니다.

## 3. 그림 방식 (C가 왜 어려운지, OCR로 해결되는지)

### C 방식이 틀리기 쉬운 이유

AI는 도형을 보면서 그리는 게 아닙니다. 좌표 숫자를 글로 추정해 쓰고, 그 숫자가 SVG 코드가 됩니다. 문제는 세 가지입니다.

- **계산 오류:** "변이 3, 4, 5인 직각삼각형"은 AI가 `(0,0) (120,0) (0,90)` 같은 좌표를 어림해서 씁니다. 이때 비율이 맞는지 스스로 계산하지 않습니다. 부채꼴은 호의 끝점을 sin/cos로 계산해야 하는데, 여기서 각도가 자주 어긋납니다.
- **글과 그림의 불일치:** 글에는 "중심각 120°"라고 쓰고 그림은 90°처럼 그려도, 코드만 봐서는 알 수 없습니다. 눈으로 봐야 알고, 눈으로 보는 것도 정밀하지 않습니다.
- **배치 문제:** 꼭짓점 이름(A, B, O)이나 각도 표시가 선과 겹치기 쉽습니다.

검증도 어렵습니다. SVG 좌표를 읽어 길이와 각도를 재는 검사기를 만들 수는 있지만, 도형마다 따로 만들어야 합니다. 그러면 사실상 B 방식(템플릿)을 새로 만드는 셈입니다.

### 제안: B+ (구조 명세 방식)

고정 템플릿 대신 AI가 도형의 구조를 JSON으로 적고, 코드가 좌표를 계산해 그립니다. 예시는 아래와 같습니다.

```
{ "type":"sector", "center":"O", "radius":6, "angle":120, "labels":["A","B"] }
{ "type":"polygon", "vertices":["A","B","C"], "sides":{"AB":3,"BC":4,"CA":5}, "mark_right_angle":"B" }
{ "type":"coordinate_plane", "points":{"A":[2,3],"B":[-1,4]}, "lines":[...] }
```

- 도형 종류를 늘리는 건 "그리기 함수"를 하나씩 추가하는 일이라 템플릿보다 유연합니다.
- 글과 그림이 같은 숫자에서 나오므로 불일치가 생기지 않습니다.
- 선분 길이나 각도 같은 수치를 코드가 계산해서 검증할 수 있습니다.

A는 완전히 제외하고 B+를 1차로 하겠습니다. 구체적인 도형 목록은 중1 교과서에 나오는 그림을 분석해서 정합니다.

### OCR은 그림 생성에 쓰이지 않습니다

OCR은 이미지 속 글자를 읽는 기술입니다. 도형 모양이나 구조는 OCR이 아니라 이미지를 직접 보는 방식으로 파악합니다. 그래서 OCR은 이 도구에서 다음 용도로 씁니다.

- **`02-3` 같은 이미지 PDF의 글자 읽기:** 이건 OCR이 맞습니다.
- **교과서·예시 문항의 그림 종류 파악:** Claude가 PDF 쪽을 이미지로 보고 "이 단원에는 부채꼴, 각기둥, 좌표평면이 쓰인다"고 정리합니다. 이 결과로 B+가 지원할 도형 목록을 만듭니다.
- **생성된 그림의 사후 점검:** SVG를 이미지로 변환해 AI가 훑어보는 보조 점검은 가능합니다. 다만 정밀 측정은 못 하므로 정확성 검증은 코드가 맡습니다.

## 4. 내보내기 형식을 HWP로 변경

1차는 PDF, 2차는 HWP로 반영했습니다. 구현할 때 고려할 점이 있습니다.

- 예전 형식인 `.hwp`(바이너리)는 외부 프로그램이 새로 쓰기 어렵습니다. 반면 `.hwpx`(XML을 압축한 형식)는 코드로 생성할 수 있고, 한컴오피스 최신 버전은 이 형식을 엽니다.
- 한글의 수식은 LaTeX가 아니라 한컴 고유의 수식 문법입니다. 그래서 LaTeX를 한컴 수식으로 바꾸는 변환기가 필요합니다. 이 변환이 2차에서 가장 큰 작업입니다.
- 이 부분은 구현 단계에서 실제 파일로 테스트하며 확인하겠습니다.

## 5. 숫자 후보를 만드는 코드의 설계 방식

### 핵심 아이디어

"답이 깔끔하게 떨어지는 숫자 조합"을 조건으로 정의하고, 코드가 그 조건을 만족하는 조합만 골라냅니다.

예시는 부채꼴의 호의 길이와 넓이 문항입니다.

1. **변수 범위:** 반지름 r은 3~12 사이 자연수, 중심각 θ는 {30, 45, 60, 90, 120, 135, 150, 180, 240, 270, 300}도입니다.
2. **공식으로 정답 계산:** 호의 길이 `2πr·θ/360`, 넓이 `πr²·θ/360`을 SymPy로 계산합니다.
3. **조건 필터:**
   - π의 계수가 정수이거나 단순한 분수일 것
   - 중간 계산이 너무 크거나 복잡하지 않을 것
   - 두 값이 같거나 의미 없이 쉬운 경우(θ=180 등)는 난이도 설정에 따라 제외할 것
4. **난이도 반영:** 쉬움은 계산 단계가 1~2번이고 숫자가 작은 조합을, 어려움은 단계가 많고 역산이 필요한 조합을 고릅니다.
5. **오류 분석형 문항:** 학생이 흔히 하는 실수(공식 혼동, 단위 오류)를 코드가 그대로 계산해 "틀린 풀이"의 값도 함께 만듭니다.
6. **출력:** 문제 숫자, 정답, 중간 풀이값, 오답 후보를 한 묶음으로 만들어 AI에 넘깁니다. AI는 이 묶음으로 상황과 문장을 씁니다.

### 생성 후 검사

AI가 쓴 글 안의 숫자가 후보 묶음과 일치하는지 코드가 확인합니다. 예시 풀이 속 계산도 다시 계산해서 맞는지 봅니다.

### 이 방식의 한계

"문제 구조(변수, 범위, 정답 공식, 조건)"를 문항 유형마다 정의해야 합니다. 이걸 사람이 전부 코딩하면 성취기준마다 큰 작업이 됩니다. 해결책은 다음과 같습니다.

- AI가 성취기준과 과제 패턴에 맞는 **구조 명세(JSON)** 를 초안으로 작성합니다. 변수 범위, 공식, 필터 조건이 들어갑니다.
- 코드는 이 명세를 제한된 수식 해석기로만 실행합니다. AI가 만든 임의 코드를 그대로 실행하지는 않습니다.
- 한 번 검수한 명세는 저장해서 재사용합니다.
- 개념 설명형이나 규칙 탐구형처럼 숫자가 핵심이 아닌 문항은 이 단계를 건너뜁니다.
