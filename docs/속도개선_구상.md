# 문항 생성 속도 개선 구상 (G3 중심)

작성 2026-10-22. 아직 구현하지 않은 구상이며, 효과는 모두 추정이다(측정 계획은 맨 아래).

## 현재 상태 (로그 21개, 호출 약 140회 실측)
| 단계 | 평균 시간 | 출력 토큰 | 비중 |
|---|---|---|---|
| G3 (소문항·채점·예시답안·검산식) | 123초 | 약 19,000 | 67% |
| AI 점검 | 49초 | 약 6,700 | 17% |
| G1 설계 | 22초 | 약 2,900 | 9% |
| G2 제시문 | 11초 | 약 1,400 | 5% |
| G0 평가 요소 | 6초 | 약 760 | 3% |
- 시간 ≈ 출력 토큰 ÷ 초당 약 120~155토큰. G3는 실제 저장되는 JSON이 약 5,200~5,900토큰인데 출력은 약 19,000토큰 → **약 70%가 모델의 내부 추론(thinking) 토큰**으로 추정(글자 수 기반 추정, 직접 측정 아님).
- 지금 호출은 `effort`와 `thinking`을 지정하지 않는다(`scripts/gen/common.py`/`generate.call`에 설정 없음). claude-sonnet-5-5의 기본값은 effort `high` + 적응형 추론이라, **추론이 길어지는 기본 설정 그대로 쓰고 있다.**

## 모델 설정으로 가능한 것 (claude-api 자료 기준, 2026-10-22 확인)
- `output_config={"effort": "low"|"medium"|"high"|"xhigh"|"max"}`: 추론 깊이·전체 토큰 사용을 줄이는 **가장 직접적인 수단**. Sonnet 5.5 기본은 `high`이고 단계가 이전 Sonnet 5와 다시 보정되었다(자료 설명: 에이전트형 작업은 `medium`부터, 채팅은 `low`). 낮출수록 빠르고 싸지만 품질이 떨어질 수 있어 **측정 후 단계별로** 정한다.
- `thinking={"type": "between_tools"}`: 추론을 끄는 방법. 단 effort `high` 이하에서만 되고 다른 필드와 같이 못 쓴다. `{"type": "disabled"}`는 400 오류. 도구 호출이 없는 이 파이프라인에서는 글쓰기 품질 영향이 커서 **후순위**.
- `temperature`/`top_p`/`top_k`: Sonnet 5.5는 기본값이 아닌 값을 보내면 400, 2026-10-21부터는 모든 모델에서 400이다. **우리 코드는 보내지 않으므로 문제없음**(코드 검색으로 확인). 결과가 매번 다른 것은 이 때문에 고정할 수 없다.
- 스트리밍: 이미 `messages.stream` 사용 중.
- 프롬프트 캐싱: 비용(캐시 읽기 입력 $0.20 vs $2 per 100만 토큰, 같은 표 기준)을 줄이고 입력 처리 시간을 약간 줄인다. 시간의 대부분이 출력이라 **속도 효과는 작다.** 같은 성취기준·책으로 여러 번 생성할 때 비용 절감용.
- 배치 API: 50% 할인이지만 비동기라 화면용 생성에는 부적합(대량 일괄 생성에는 가능).
- 빠른 모드(fast mode): Opus 계열에서만 지원. 현재 모델에는 해당 없음.

## 구조로 줄이는 방법
1. **effort 단계별 차등**: 시간이 가장 긴 G3, AI 점검에서 효과가 크다. 예: G0·G1·G2 `low`, G3 `medium`, AI 점검 `medium`. (품질 시험 필요)
2. **독립 단계 병렬화(품질 영향 없음)**: 풀이 판정(약 7초)과 AI 점검(약 49초)은 서로 입력만 공유하므로 동시에 호출하면 약 7초 단축.
3. **G3 소문항별 분할 병렬 호출**: 3개 소문항을 동시에 쓰면 G3 시간을 최대 1/3까지 줄일 수 있으나, 조건·수준 서술·의존 관계의 일관성이 깨질 수 있다. 공통 골격(제시문·평가 요소·소문항 설계)을 고정해 주고 각자 나머지를 쓰게 하는 설계가 필요. **효과는 크지만 위험도 큼.**
4. **G3 출력 줄이기**: 예시답안·검산식(checks)의 중복을 줄이거나 코드가 만들 수 있는 부분(검산 기대값 등)을 코드로 옮긴다. 출력 토큰이 곧 시간이다.
5. **재시도 줄이기**: 검증에서 오류가 나면 G3를 다시 쓰는데 이때 45~60초가 더해진다. 자주 걸리는 오류를 프롬프트로 미리 막는다(조사·W8 발문 끝 표현 등).
6. **화면 체감 개선(실제 시간은 그대로)**: 단계별 진행 표시, 제시문과 설계가 나오면 먼저 보여 주기.

## 측정 계획 (아직 실행 안 함, 사용자 승인 후)
- 같은 (성취기준, 책, 시드)로 G3 effort를 `high`(현재) / `medium` / `low`로 바꿔 각 2회 = 6건, 약 $3~4(추정).
- 비교 항목: G3 시간, 출력 토큰, 검증 오류·재시도 횟수, AI 점검 이슈 수, 블라인드 식별 정확도(`blind_identify.py`), 반영도 지표(`reflect_score.py`).
- 합격 기준 예: 시간이 30% 이상 줄고 검증 오류와 점검 이슈 수가 늘지 않으며 책 식별 정확도가 유지되면 채택.
- 병렬화(2번)는 품질 영향이 없어 바로 구현 가능, 3번은 별도 품질 시험 필요.

## 비용 단가 확인 필요
claude-api 자료의 모델 표(2026-10-06 기준)는 Sonnet 5.5를 입력 $2 / 출력 $10 (100만 토큰당)으로 적고 있다. 이 프로젝트의 비용 추정은 $3 / $15를 써 왔으므로 **실제 비용은 추정의 약 2/3일 수 있다.** 콘솔의 실제 청구액과 대조해 단가를 고쳐야 한다(미반영).
