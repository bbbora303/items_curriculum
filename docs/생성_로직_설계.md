# 수학 문항 생성 로직 설계 (v0, 검토용)

국어 설계 4-7(G0~G3)을 수학용으로 옮긴 것. ❓는 확정 전 검토 필요. 구현은 이 문서 확정 후.

## 1. 전체 흐름

```
입력(교사) ─> G0 후보 제안 ─> 교사 확정 ─> G1 설계 ─> [코드] 수치 선택 ─> G2 상황·그림
          ─> G3 소문항·채점기준·예시답안 ─> [코드] 조립 ─> [코드] 검증·검산 순환
          ─> AI 점검 ─> 교사 검토 ─> 저장
```

| 단계 | 담당 | 하는 일 | 결과 |
|---|---|---|---|
| 입력 | 교사 | 성취기준(1~3), 총점, 응답 유형, 과제 패턴(자동/선택), 난이도, 출판사(기본 '미선택') | 생성 입력 |
| **G0** | AI | 평가 요소('~하기') 후보 3~5개, 교과 역량 후보를 성취기준·성취수준에서 제안 | 후보 목록 |
| 확정 | 교사 | 평가 요소·역량 선택·수정 (국어와 동일한 3단계 분리) | 확정 평가 요소 |
| **G1** | AI | 과제 패턴 선택, 소문항 구성, 소문항별 겨냥 성취수준·배점 배분, 필요한 그림·수치 명세 지정, 풀이 방법 계획 | 설계 JSON |
| 수치 선택 | **코드** | 수치 명세에서 제약을 만족하는 후보를 뽑아 `numberBinding` 확정 | 숫자와 파생값(정답) |
| **G2** | AI | 상황 문장, 그림 params 작성 (숫자는 코드가 준 값만 사용) | stimulus |
| **G3** | AI | 소문항 발문, 조건, 수준 서술, 풀이 방법별 예시답안과 검산 식, 채점 시 유의점, 교사 확인 사항 | 소문항 등 |
| 조립 | 코드 | 단계 결과를 문항 JSON으로 합치고 배점 합 확인 | item JSON |
| 검증 순환 | 코드 | `validate_item.py`(M1~M29), 오류는 AI에 되먹임해 최대 3회 재생성 | 오류 0개 |
| 본문 숫자 대조 | 코드 | 본문·발문 속 숫자가 `numberBinding`과 일치하는지 | 일치 |
| AI 점검 | AI | 수준 서술 일관성, 발문 모호성, 풀이 서술 정확성 점검. 심각하면 1회 자동 수정 | 점검 의견 |
| 교사 검토 | 교사 | 체크리스트 참고, '검토 완료' 버튼 | 저장 |

## 2. 국어와 달라지는 핵심

1. **숫자는 AI가 정하지 않는다.** 코드가 수치 명세에서 뽑아 주고, AI는 그 숫자만 쓴다.
2. **정답은 코드가 검산한다.** AI가 쓴 예시답안의 식(`checks`)을 SymPy로 다시 계산해 기대값과 비교한다. 불일치하면 오류로 AI에 되먹임한다.
3. **그림은 AI가 직접 그리지 않는다.** AI는 도형 구조(params)만 쓰고 코드가 SVG를 만든다(B+).
4. **풀이 방법은 2개 이상**(배점 3점 이상 소문항). G3가 방법별 예시답안을 쓴다.
5. **교사 확인 사항**을 G3가 제안한다. 자료에서 반복 확인된 8가지 유형(그래프 점 연결, 눈금 벗어남, 근삿값 허용, 중복 식 처리, 학교별 배점 조정, 기호 정확성, 계산 실수와 개념 오류 구분, 열린 과제 확인) 중 이 문항에 해당하는 것을 고른다.
6. **채점 시 유의점**은 확인된 문구 목록(연쇄 오류 인정, 표현이 달라도 인정, 단위 정책 등)에서 고르고 문항에 맞게 다듬는다. 감점 규칙은 쓰지 않는다.

## 3. 단계별 AI 입력·출력 계약

### G0 (평가 요소·역량 제안)
- 입력: 성취기준 본문·해설, 성취수준 A~E, 영역, 내용 요소, (선택) 출판사 단원 정보
- 출력: `evaluationElementCandidates[]`(text '~하기', 근거 성취수준), `competencyCandidates[]`
- 규칙: 평가 요소는 성취기준에 없는 내용을 만들지 않는다. 성취기준 해설의 제한 사항(예: "복잡한 계산은 다루지 않는다")을 지킨다.

### G1 (설계)
- 입력: 확정 평가 요소, 총점, 응답 유형, 난이도, 사용 가능한 과제 패턴(성취기준과 `standardsExamples` 일치), 사용 가능한 수치 명세, 사용 가능한 그림 유형
- 출력: `taskPattern`, `subQuestions[]` 골격(no, 역할, answerType, maxScore, targetLevels, dependsOn), `numSpecId`(없으면 null), `figuresNeeded[]`, `solutionMethodsPlan[]`
- 규칙: **쉬운 계산 -> 설명 -> 판단** 순서로 난이도가 올라가고, 앞 소문항 결과를 뒤에서 사용한다. 마지막 소문항 배점이 가장 크다. 소문항 배점 합 = 총점.

### G2 (상황·그림)
- 입력: G1 결과, `numberBinding`과 파생값(AI는 수정 불가), 그림 유형 목록과 params 형식
- 출력: `stimulus.text`, `figures[]`(type, params)
- 규칙: 숫자는 입력으로 받은 값만 쓴다. 실제 기관·사람 이름, 출처가 필요한 통계는 쓰지 않는다. 중1 수준 어휘.

### G3 (소문항·채점기준·예시답안)
- 입력: G1·G2 결과, 파생값, 과제 패턴의 수준 서술 형식, 채점 시 유의점·교사 확인 사항 후보 목록
- 출력: 소문항 발문, `conditions[]`, `evaluationElements[]`(수준 서술 포함), `solutionMethods[]`, `modelAnswers[]`(`checks` 포함), `scoringNotes[]`, `teacherChecks[]`, `feedbackNotes[]`
- 규칙: 수준 서술은 "정확하게 / 일부 오류 / 부분적으로 / 어려움이 있음" 계열 표현을 쓰고, 최하 수준 1점. 조건은 반드시 수준 서술에 반영. 예시답안의 모든 계산 결과를 `checks`로 제시.

## 4. 부분 재생성 (4가지, 국어 6번과 동일 + 1)

| 선택 | 다시 만드는 것 | AI 호출 |
|---|---|---|
| 제시문(상황·그림)만 | G2 -> 영향받는 G3 일부 | 있음 |
| 소문항·채점기준만 | G3 | 있음 |
| 전체 | G1~G3 | 있음 |
| 수치만 바꾸기 (**수학 추가**) | 같은 구조, 다른 숫자 | **없음(코드)** ❓ |

❓ **수치만 바꾸기를 AI 호출 없이 하려면** 본문과 예시답안을 플레이스홀더 템플릿으로 저장해야 한다. 예: `반지름이 {{r}} cm이고 중심각이 {{theta}}°` / 정답 `{{arc|latex}}`. 코드가 새 숫자로 채운다. 장점: 즉시, 무료, 정답이 항상 일치. 단점: G2·G3가 템플릿 형식으로 써야 해서 프롬프트가 복잡해지고, 숫자에 따라 문장이 어색해질 수 있다(예: 분수). 제안: **템플릿 방식 채택**, 어색해지면 '전체 재생성'으로 처리.

## 5. 교과서 연계 (국어 결정과 동일)
- 출판사 선택: 동아, 미래엔, 비상, 천재(김동재), 천재(김화경), **미선택(중립)**.
- 반영 수준: 개념·용어·학습 요소, 유사 소재 새 글. 교과서 원문·문제 사용은 고도화.
- 현재 자료: 단원·소단원 구조(`textbook_units_math1.json`)만 있다. 용어·예제 수준 반영은 교과서 상세 분석(API)이 필요하다. 상세 분석 전에는 '미선택'과 단원 이름만 반영한다.

## 6. 검증 순환 상세
1. 조립 직후 `validate_item.py` 실행
2. 오류 목록을 오류 번호와 함께 해당 단계(G3 우선)에 되먹임하고 재생성. 최대 3회
3. 3회 후에도 오류면 교사에게 '오류 있음' 상태로 표시하고 오류 내용을 보여준다
4. 코드 검산 불일치(M26)는 **AI의 예시답안을 코드값에 맞춰 고치게** 하며, 코드값을 AI 값에 맞춰 바꾸지 않는다
5. 오류 0개가 되면 AI 점검으로 진행

## 7. 비용과 호출 수 (추정, Sonnet 5.5 가정)
- 한 문항 세트 생성: G0 1회 + G1 1회 + G2 1회 + G3 1~3회 + AI 점검 1회 = 평균 5~7회
- 입력·출력 토큰이 국어보다 작을 가능성(지문이 짧음) / 단, 수식·표가 많아 출력이 늘 수 있음
- 국어 프로토타입과 같은 수준(문항 세트당 약 $0.1~0.3)으로 예상. 실제 값은 첫 시험 후 확인

## 8. 확정된 결정 (2026-10-20)

| 항목 | 결정 | 구현 |
|---|---|---|
| 수치만 바꾸기 | **템플릿 방식.** 본문·예시답안을 `{{r}}`, `{{arc\|latex}}` 같은 자리표시자로 저장하고 코드가 새 숫자를 채운다. 문장이 어색해지면 전체 재생성 | `scripts/template.py`, `scripts/gen/renumber.py` |
| 과제 패턴 선택 | 교사가 직접 고르는 옵션을 둔다. 기본은 자동(AI 선택) | `--pattern auto\|id`, `--list-patterns` |
| 수치 명세가 없는 성취기준 | **AI가 명세 초안(변수 범위, 정답 공식, 깔끔함 조건)을 만들고, 교사가 쉬운 말 설명을 보고 확정한다.** 확정 후에는 코드가 그 명세로 숫자를 고른다. 명세가 있으면 바로 생성 | GN 단계, `data/numspecs_draft/` -> `data/numspecs/`, `--approve-spec`(시험용 `--auto-approve-spec`) |
| 난이도 | 쉬움·보통·어려움 3단계로 시작. 5단계는 고도화 | `easy/medium/hard` |
| 내보내기 | 1차 PDF, 2차 HWPX(교사들이 주로 HWP로 작업). LaTeX -> 한컴 수식 변환이 핵심 작업 | 미구현 |

## 9. 템플릿 방식의 세부 규칙
- 자리표시자 `{{식}}`의 식은 수치 명세의 변수·파생값과 안전한 식만 쓴다. `{{식|latex}}`는 π·분수를 LaTeX로 쓴다.
- 문자열 전체가 `"{{r}}"` 하나이면 숫자 값으로 채워진다(그림 params).
- 검산 식(`checks`)은 `vars` 없이 변수·파생값 이름으로 쓴다(예: expr `2*pi*r*theta/360`, expected `arc`).
- **수치 변경 시험:** 생성 직후 코드가 다른 숫자 2조합으로 채워 검증기를 다시 돌린다. 숫자를 고정으로 쓴 곳이 있으면 오류나 경고로 잡혀 G3에 되먹임된다.
- **표·자료가 핵심인 문항**(점수 20개, 줄기와 잎 그림 등)은 현재 스칼라 변수 명세로 표현할 수 없어 템플릿을 쓰지 않는다. 숫자는 AI가 정하고 코드가 검산만 한다. 데이터 생성기(자료 명세)는 후속 과제.
- 교사 확정 단계: 명세 초안의 `plainSummary`(쉬운 말), 후보 개수, 예시 조합 3개를 보여 주고 확정/수정을 받는다. 현재는 CLI 플래그로 대신한다.
